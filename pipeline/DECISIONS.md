# 決めたことの記録

設計書（開発パイプライン v3）から変えた点と、進めるうちに決めたことを、日付つきで残す。新しいものが下。

## 2026-10-10（S0）

### D-001 開発は、Claudeアプリが用意する作業環境の中で行う
- v3 では「Claude Code、Node.js、Git を PC に入れる」をユーザーの作業にしていた。
- 実際には、Claudeアプリが PC の上に用意する作業環境（Linux）に Node.js 22 と git があり、接続したフォルダを直接扱えた。
- そのため、Windows 側には何も入れない。ユーザーの導入作業はなくなった。

### D-002 依存とビルドは作業用コピーで行い、正本はこのフォルダに置く
- このフォルダは OneDrive の中（`OneDrive\Desktop\idle game`）にある。node_modules を置くと同期が重くなる。
- 接続フォルダの上では、削除に許可が要るなどの制限がある。
- そこで `scripts/vm/run.sh` が、毎回このフォルダから作業用コピーを作り、そこで検査とビルドを行う。
- ソースと履歴（.git）はこのフォルダにあるので、OneDrive がそのままバックアップになる。

### D-003 保護ファイルは、フックではなくスクリプトの照合で守る
- v3 では「フックで書き込みを止める」としていたが、この作業環境ではフックが働くことを確かめられない。
- 代わりに、承認時の指紋と照合する `scripts/check/protected.ts` を全検査と play の前に走らせる。
- 承認は `pipeline/APPROVALS.md` に日付と理由つきで残り、`status` に直近3件が表示される。
- 限界: これは「黙って変わったら気づける」仕組みで、書き換え自体を物理的に止めるものではない。

### D-004 コマンドは言葉で受ける
- `/status` などはアプリのコマンドとして登録されない。ユーザーは「status」「play」などの言葉を打つ。
- 手順は `pipeline/commands/` にあり、実体は `scripts/` のスクリプト。

### D-005 画面を自動で操作するテスト用のブラウザは、S3 で方法を決める
- 作業環境からは、テスト用ブラウザの配布元に到達できなかった。
- S3 で通し操作テストを作るときに、実行場所を決める（Claude 側の環境にはブラウザがある）。

### D-006 公開先は未決定
- 作業環境から到達できたのは GitHub だけで、Cloudflare と Netlify には到達できなかった。
- ユーザーと相談して決める。

### D-007 公開先は GitHub Pages（ユーザーの選択）
- 毎回の play で自動的に公開できることを優先した。無料枠の条件として、リポジトリは公開になる。
- 鍵（トークン）は `.secrets/github-token.txt` に置く。履歴の対象外（.gitignore）で、対象は1つのリポジトリ、権限は内容の読み書きだけ。
- `scripts/publish.ts` は、送る前に「鍵が履歴にも公開物にも入っていないこと」を確かめ、入っていれば中止する。
- 公開用の枝（gh-pages）に dist/ を送り、あわせて履歴（main）とビルド番号を送ってバックアップにする。
- 作業環境からは `*.github.io` に届かないので、公開URLそのものの確認は、Claude 側の別の経路とユーザーの iPhone で行う。

### D-012 S3 の作り方（2026-10-11）
- **戦闘の表示は、まだ PixiJS を使わない。** 灰色試作には絵がないので、箱と体力の棒を HTML/CSS で出している

  表示は「出来事の列を時間どおりに再生するだけ」なので、表示の作り替えはルールに影響しない。
- **通し操作テストは2段にした（D-005 の結論）。**
  - `tests/flow.test.ts`: 進行役（`src/ui/session.ts`）を、にせの時計と保存領域で動かす。ブラウザが要らないので、
    全検査の一部として、ユーザーのPCの作業環境でも毎回走る。

  - `play` と S3 の出口は、`scripts/check/e2e-gate.ts` で「合格の記録があり、指紋がいまのソースと同じ」ことを確かめる。
    ソースを変えたら、通し操作テストをやり直すまで play は通らない。
  - 限界: 記録は Claude が実行して置いたもので、ユーザーのPC上で再実行して確かめたものではない。
    また、使っているのは Chromium で、iPhone の Safari そのものではない。Safari だけで起きる不具合は、ユーザーの実機で見つかる。
- **画面の構成**: 下のタブ5つ（旅、団員、編成、勧誘、その他）。団員の詳細はポップアップ、章の一覧と設定は「その他」に入れた。

  確認用の機能（速度変更、時間送り、付与）を使うと「使用あり」と残り、その記録は採点に使わない。
- **題名は仮**: 画面の題名とホーム画面の名前を「旅の劇団」としてある。正式な題名は、ユーザーが決める。

### D-014 第2版の作り（2026-10-11）
- **セーブ**: ゲーム本体の版を 2 に上げた。第1版（build-4 まで）のゲームは引き継がない
  （面の進み方も通貨も違うので、変換しても意味のある状態にならない）。開いたときに、前のセーブを退避してから
  最初から始め、そう知らせる。起動の回数は残る。プレイの記録も、新しいゲームのものとして始め直す。
  この動きは、ユーザーの build-4 の実物のセーブ（`tests/fixtures/save-build-4.json`。端末の情報は含まない）でテストしている。
- **放置報酬は、始めた時点からたまる**（1面も突破していないうちは、1面のぶん）。そうしないと、1面で負けたときに、
  おひねりを得る方法がなくなって進めなくなる。
- **画面の構成**: 下のタブ6つ（旅、団員、編成、相棒、勧誘、ミッション）と、上の帯の「≡」（旅の記録と設定）。
  画面は7つで、上限（10）の内側。日課は、ミッションの画面の上半分に置いた。
- **箱の中身は、数字だけを書き換える**。毎秒変わるので、画面ごと描き直すと、押している途中のボタンが作り直されて
  押し損ねる。変わり続ける値には `data-live` を付け、あとから書き込む（`pipeline/rules/ui.md`）。
- **「まとめて勧誘」「まとめて受け取る」は、画面の側のくり返し**。ルール（core）は1回ぶんだけを持つ。
- **開き直した直後の戦闘は、再生しない**。再生用のデータはセーブに入れていないので、「戦闘中…」と出して結果を待つ
  （戦闘は長くても60秒）。
- **負けたとき**: 旅の画面に「稽古が足りない！」と、団員の画面へ行くボタンを出す。勝てる見込みは、どこにも出さない（決定19）。
- **数値の作り**: 進む速さの山と谷は、面ごとの敵の伸びの表（`params/base.json` の `stageGrowth`）で作る。
  2-10 までは止まらず、3-1 で一段上がり、3-2〜3-5 がゆるい壁、3-6 から先が大きな壁。
  本ごとのばらつきを抑えるため、昇格の伸びは 1つ10%、ダメージのばらつきは ±6% にした。
- **模擬プレイの遊び方**: 勝てる見込みは見ない。負けたあとは、「団員のレベルが合わせて2つ上がったら」か
  「4分待ったら」、もう一度挑む（ふつうの人）。
- **合否の数字の結果**: 9項目のうち8項目が合格。「新しい面を突破できなかった時間の最長」だけが、6分以下の決まりに対して
  6.88分で不合格。原因は数値の調整不足ではなく、決まりどうしの関係にある。「12分までは負けない」（ここまでで約20面進む）と
  「30分で26面目まで」を両方守ると、残りの18分で進めるのは5〜6面で、1面に平均3分あまりかかる。
  負けて稽古してもう一度負けると、その面だけで6分を超える。
  → 2026-10-11、理由を示してユーザーの承認を得て、この1項目を「6分以下」から「8分以下」に変えた（ほかの数字と数値は変えていない）。
  これで9項目すべて合格。
- **宿題（7日分の設計。G1 のあと）**: 40面のうち25面を最初の30分で使っている。レベルの上限（40）に、30分で31まで届く。
  4章の敵の伸びは仮。初クリア報酬のおひねりは小さい（進む速さが、余分なおひねりにとても敏感なため）。
  日課の報酬（おひねり10分ぶん × 2）を受け取る時期で、序盤の進みが変わる。
  模擬プレイの間合い（1面あたり約33秒）は推測なので、ユーザーの次のプレイの記録で合わせ直す。
